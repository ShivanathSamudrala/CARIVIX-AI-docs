# CARIVIX AI — Database Integration

## 1. Purpose

This document explains how the CARIVIX AI backend **connects to and works with the database**.

It covers:

| # | Topic |
|---|---|
| 1 | Database operations supported by the backend |
| 2 | Error handling |
| 3 | API integration |
| 4 | Technical issues identified and resolved |
| 5 | Testing completed to verify the database service |

---

## 2. Database Service

All database operations in the backend are handled through a **dedicated Database Service**.

> Different parts of the application **do not directly manage database operations**. Instead, they use this service to perform database-related tasks.

### Connection Lifecycle

The service manages the complete database connection process:

| Step | Action |
|---|---|
| 1 | Opening the connection |
| 2 | Performing the required operation |
| 3 | Closing the connection properly after the operation is completed |

> The connection is also closed correctly when an **error occurs** during the operation.

### Benefit

This approach keeps database operations **organized** and provides **one common point** for handling database-related logic.

---

## 3. Supported Database Operations

The Database Service supports the following operations.

### 3.1 Record Storage

| Capability | Description |
|---|---|
| Single Record | Store a single record |
| Multiple Records | Store multiple records in one operation |
| Batch Operations | Multiple records written together instead of requiring separate database calls for every record |

### 3.2 Data Retrieval

Records can be retrieved from a **selected database table**.

The retrieval operation also supports **filtering** using a specific field and value.

### 3.3 Filtering and Pagination

Filtering can be **combined with pagination**.

| Parameter | Purpose |
|---|---|
| **Limit** | Controls the number of records returned |
| **Offset** | Controls the number of records skipped before the results are returned |

> This allows large datasets to be retrieved in **smaller sections** instead of loading the complete table at once.

---

## 4. Database Error Handling

Database operations are handled through **specific error handling** within the service.

### Error Conversion

> Database failures are caught and converted into **named error types** instead of exposing low-level database errors directly to the calling application.

**Example:** Attempting to write data to a table that does not exist produces a **clear, database-specific error**.

### Benefit

This allows the API layer and other calling components to:

- Handle database failures in a **consistent way**
- Return **appropriate error responses**

## 5. Technical Issue Identified and Resolved

### Issue Description

During development, an issue was identified when **date values generated by the processing workflow were sent to the database**.

> The database engine did not directly support the specific **date or timestamp data type** being passed by the processing workflow. This caused the database write operation to **fail**.

### Resolution

The database integration was updated to:

- **Convert date and timestamp values into plain text** before writing them to the database

### Verification

| Step | Result |
|---|---|
| Same scenario tested again after fix | ✅ Data successfully stored |
| Automated regression test added | ✅ Ensures this issue does not return in future changes |

---

## 6. API Integration

The Database Service is connected to **three API endpoints**.

### 6.1 Store Endpoint

> The store endpoint accepts records and writes them to a **named database table**.
>
> The table is **created automatically** when it does not already exist.

### 6.2 Retrieve Endpoint

> The retrieve endpoint reads records from a **named table**.
>
> It supports **filtering and pagination** to control the returned results.

### 6.3 Combined Pipeline Endpoint

> The combined pipeline endpoint performs **data processing and database storage in one request**.
>
> This provides a **simpler integration point** for other domains because they do not need to:
> - Make separate processing and storage requests
> - Manage the processed data between the two operations

## 8. Current Database Limitation

### Single Fixed Database File

> The current database setup uses a **single fixed database file**.
>
> It does **not yet use a configurable connection** to a production-grade database system.

**Impact:** The current data is stored in **one fixed location**.

**Status:** Moving to a configurable production-grade database is identified as a **future development requirement**.
