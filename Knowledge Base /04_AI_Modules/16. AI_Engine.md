## 1. Overview

The CARIVIX AI Engine is the core AI processing component responsible for converting user queries and project knowledge into context-aware AI responses.

**The Engine Combines:**

- Natural-language query processing
- Document intelligence
- Document ingestion
- Text preprocessing
- Document chunking
- Metadata handling
- Text embeddings
- Semantic/vector retrieval
- FAISS vector search
- Retrieval-Augmented Generation
- Prompt processing
- Local LLM inference
- Grounded response generation
- AI evaluation
- API integration

**Overall Processing Flow:**

```text
User Query → Query Processing → Embedding → Retrieval → Context → Prompt → LLM → Response
```

The architecture is designed so that the LLM receives relevant project information retrieved from the CARIVIX knowledge base rather than relying only on its pretrained knowledge.

---

## 2. Objectives

The main objectives of the AI Engine are:

- Process natural-language user queries
- Convert documents into machine-readable knowledge
- Convert textual information into vector representations
- Store and retrieve relevant information efficiently
- Provide relevant context to the LLM
- Generate responses based on retrieved information
- Reduce irrelevant information being passed to the LLM
- Support document-based question answering
- Validate retrieval and generated-response quality
- Provide an API-accessible AI processing layer

The engine is therefore not just an LLM wrapper. It consists of multiple processing layers working together.

## 5. Document Intelligence Pipeline

The first major part of the AI Engine is the Document Intelligence pipeline. Documents may contain large amounts of unstructured information that cannot efficiently be sent directly to an LLM. Therefore, documents are transformed into structured retrieval units.

**Processing Sequence:**

```text
Document → Loading → Text Extraction → Cleaning → Chunking → Metadata → Embedding → Vector Index
```

This pipeline converts raw project documentation into searchable AI knowledge.

---

## 6. Document Ingestion

Document ingestion is responsible for bringing source information into the AI Engine. The ingestion layer receives documents and prepares their textual content for downstream processing.

**Major Operations:**

- Identify source document
- Load document
- Extract text
- Normalize text
- Remove unnecessary formatting
- Prepare content for chunking
- Preserve document-level information

**Ingestion Flow:**

```text
Source Document → Document Loader → Text Extraction → Text Cleaning → Normalized Content → Chunking
```

The ingestion stage is important because poor source extraction can affect every subsequent stage of the RAG pipeline.

---

## 7. Document Chunking

Large documents are divided into smaller pieces called chunks. Chunking is required because retrieval works more effectively when individual searchable units contain focused information.

**Current Architecture:**

| Parameter | Value |
|---|---|
| Chunk Size | ~500 |
| Chunk Overlap | ~50 |

**Chunking Architecture:**

```text
Large Document → Text Splitter → Chunk 1 / Chunk 2 / Chunk 3 / Chunk N → Embedding
```

The overlap preserves some information between neighboring chunks.

The chunking strategy directly affects retrieval quality because chunks that are too large may contain unrelated information, while chunks that are too small may lose important context.

---

## 8. Metadata Management

Metadata is maintained alongside document chunks.

**Typical Metadata Includes:**

- Source document
- Document identifier
- Chunk identifier
- Document type
- Source location
- Processing information

**Metadata Relationship:**

```text
Source Document → Chunk → Chunk Text → Embedding → FAISS
                      → Document Metadata → Retrieval Information
```

Metadata provides traceability between a retrieved chunk and its original source.

---

## 9. Embedding Generation

After documents are divided into chunks, the text is converted into numerical vector representations.

**Current CARIVIX Architecture:**

```text
SentenceTransformers → all-MiniLM-L6-v2
```

The configured embedding representation is 384-dimensional.

The purpose of embeddings is to represent semantic meaning numerically so that related queries and document chunks can be compared.

Sentence Transformers documentation describes semantic search as embedding both the corpus and query into a vector space and retrieving the closest representations.

---

## 10. FAISS Vector Retrieval

FAISS is used as the vector search layer. The document embeddings are stored inside the FAISS index.

**When a User Sends a Query:**

| Step | Action |
|---|---|
| 1 | The query is converted into an embedding |
| 2 | The query vector is compared against indexed document vectors |
| 3 | Similar vectors are identified |
| 4 | The highest-ranked results are returned |
| 5 | Retrieved chunks are passed to the context-processing layer |

FAISS supports nearest-neighbor search over dense vectors and can return the top-k nearest results.

---

## 11. Semantic Retrieval

The AI Engine uses semantic retrieval rather than depending only on exact keyword matching.

For example, a query and a document may use different words while expressing a similar concept. Semantic embeddings allow the system to compare the meaning represented by vectors.

**Retrieval Process:**

```text
User Query → Query Embedding → Query Vector → FAISS Similarity Search → 
Similarity Results → Top-K Relevant Chunks → Context Assembly
```

The current project configuration uses Top-K 5 as the retrieval setting.

This retrieval layer is one of the most important components of the AI Engine.

---

## 12. RAG Architecture

Retrieval-Augmented Generation combines information retrieval with LLM generation.

**Stage 1 – Retrieval:**
The system finds relevant information from the indexed knowledge base.

**Stage 2 – Generation:**
The retrieved information is provided to the LLM together with the user's question.

**Complete RAG Flow:**

```text
User Query → Query Embedding → FAISS Retrieval → Top-K Relevant Chunks → 
Context Assembly → Prompt Template → Ollama → Llama 3.1 → 
Generated Response → Response Validation
```

This creates the core knowledge-grounded processing path of the AI Engine.

---

## 13. Context Assembly

After retrieval, the selected chunks are combined into a context package. The context contains information considered relevant to the user's query.

**Processing Sequence:**

```text
Query → FAISS Retrieval → Top-K Chunks → Relevant Text → Context Assembly → Prompt
```

Context assembly is important because the LLM should receive relevant information rather than the entire document repository.

The retrieved context therefore acts as the information bridge between the vector retrieval system and the LLM.

---

## 14. Prompt Engineering and LLM Processing

The retrieved context is combined with the user query using a prompt template.

**The Prompt Generally Contains:**

- System instructions
- User query
- Retrieved context
- Response instructions

The current architecture uses Ollama for local LLM execution and Llama 3.1 as the primary configured model.

Prompt templates provide a consistent method of passing retrieved information to the LLM.

---

## 15. Grounded AI Response Generation

The objective of the RAG architecture is to generate responses using retrieved project-specific context.

**Response-Generation Process:**

```text
Query + Retrieved Context → Prompt → LLM → Response
```

The retrieved context should provide the factual basis for the answer.

**The AI Engine Can Evaluate Whether:**

- Relevant information was retrieved
- Retrieved information was sufficient
- The response addresses the query
- The response remains consistent with retrieved context
- Unsupported information was introduced

This is particularly important for project-specific documentation and knowledge retrieval.

---

## 16. End-to-End Workflow

```text
User → FastAPI → AI Engine → Query Processing → Query Embedding → 
FAISS Search → Top-K Documents → Context Assembly → Prompt Template → 
Ollama → Llama 3.1 → Generated Response → Response Validation → 
FastAPI Response → User
```

This diagram represents the primary end-to-end technical workflow of the CARIVIX AI Engine.

---

## 17. FastAPI Integration

FastAPI provides the application interface through which the AI Engine can be accessed. The API layer provides the connection between the CARIVIX application and AI processing components.

**API-to-AI Flow:**

```text
CARIVIX Application → FastAPI → Request Validation → AI Engine → 
Query Processing → RAG Pipeline → LLM → AI Response → FastAPI → CARIVIX Application
```

The API layer therefore acts as the entry and exit point of the AI Engine.
