## 1. Overview

The CARIVIX AI Query Workflow defines how a user query is received, understood, classified, routed, processed through the appropriate AI/ML pipeline, and converted into a final response.

The workflow is designed around a hybrid AI architecture in which the query is dynamically routed to the appropriate processing path:

| Path | Purpose |
|---|---|
| ML Prediction Pipeline | Structured business/ML predictions |
| RAG Pipeline | Answering questions from indexed documents and knowledge |
| General LLM Pipeline | Queries requiring natural-language generation or reasoning |
| Intent Classification and Query Routing | Determine which pipeline should process the query |

**Key Technologies:**

- **Llama 3.1 + Ollama** – Local LLM inference
- **FastAPI** – AI inference/API interface

---

## 2. High-Level AI Query Workflow

The overall workflow is:

```
User Query
    ↓
API Request (FastAPI)
    ↓
Query Preprocessing
    ↓
Intent Classification
    ↓
Query Routing
    ↓
Selected AI Pipeline (ML/RAG/LLM)
    ↓
Context/Prediction Generation
    ↓
Prompt Construction
    ↓
Llama 3.1 + Ollama
    ↓
Response Processing
    ↓
API Response
```

---

## 3. Query Entry Point

The AI query workflow begins when a client sends a request to the CARIVIX AI API.

**API Responsibilities:**

| Responsibility | Description |
|---|---|
| Receive Request | Accept incoming API requests |
| Validate Request | Check request structure and format |
| Extract Query | Extract user query from request |
| Pass to AI Layer | Forward query to AI processing layer |
| Return Response | Send final AI response to client |

**Example Request:**

```json
{
  "query": "What were the sales units for the selected period?"
}
```

---

## 4. Query Preprocessing

Before classification, the query passes through a preprocessing stage to create a clean and consistent representation.

**Processing Activities:**

| Activity | Description |
|---|---|
| Query Validation | Ensure query exists and is valid |
| Whitespace Removal | Remove unnecessary whitespace |
| Text Normalization | Normalize text where required |
| Empty Input Handling | Handle empty or invalid input |
| Query Preparation | Prepare for intent classification |
| Original Preservation | Preserve original query for downstream processing |

**Key Design Principle:** The original query should remain available because downstream components such as RAG and the LLM may require the original wording.

---

## 5. Intent Classification

Intent classification determines what the user is trying to accomplish.

**Technology:** TF-IDF + Logistic Regression
**Dataset:** `intent_data.csv`

**Outputs:**

| Output | Description |
|---|---|
| Intent | Identified user intent |
| Confidence Score | Probability score for the prediction |

**Example:**

```json
{
  "query": "Show the expected revenue for this month",
  "intent": "ml_prediction",
  "confidence": 0.91
}
```

**Key Design Principle:** The classifier does not directly generate the final answer. Its primary responsibility is to provide information required by the query router.

---

## 6. Query Routing

After intent classification, the query is passed to the query router.

**Router Inputs:**

| Input | Description |
|---|---|
| Original Query | User's original query |
| Predicted Intent | Intent from classifier |
| Classification Confidence | Confidence score |
| Required Processing Path | Determined by intent |

**Main Routing Paths:**

| Route | Purpose |
|---|---|
| ML Prediction | Structured prediction/inference |
| RAG | Document/knowledge-based answering |
| LLM | General natural-language generation |

**Routing Decision Flow:**

```
Intent Classification Result
    ↓
Query Router
    ↓
    ├── ML Prediction ──→ Structured business/ML predictions
    ├── RAG ────────────→ Document/knowledge-based answering
    └── LLM ────────────→ General natural-language generation
```

**Key Design Principle:** This routing layer prevents every query from being processed using the same AI mechanism.

---

## 7. ML Prediction Workflow

Queries requiring structured ML inference are sent to the ML model service.

**ML Workflow Steps:**

| Step | Description |
|---|---|
| 1 | Extract required input features |
| 2 | Validate model input |
| 3 | Load configured baseline model |
| 4 | Execute model inference |
| 5 | Generate prediction results |
| 6 | Format prediction output |

**ML Pipeline Flow:**

```
API Layer
    ↓
Model Service
    ↓
Model Configuration
    ↓
Model Loader
    ↓
Preprocessing
    ↓
Trained Model (.pkl)
    ↓
Inference
    ↓
Output Formatter
```

**Key Design Principle:** The model-service structure separates model loading, preprocessing, inference, and response formatting.

## 10. Document Processing Pipeline

Before a document can be used for query answering, it must be converted into searchable knowledge.

**Document Processing Flow:**

```
Documents
    ↓
Document Loader
    ↓
Document Processing
    ↓
Chunking
    ↓
Embedding Generation
    ↓
Vector Database
```

**Key Design Principle:** The document-processing workflow prepares the knowledge base used by the online RAG query workflow.

---

## 11. Chunking

Large documents are divided into smaller chunks before embedding.

**Purpose of Chunking:**

| Purpose | Description |
|---|---|
| Context Relevance | Keep retrieved context relevant |
| Semantic Search | Improve semantic search accuracy |
| LLM Optimization | Avoid sending unnecessary content to LLM |
| Retrieval Efficiency | Make document retrieval more efficient |
| Context Focus | Provide focused context for answer generation |

**Key Design Principle:** Each chunk can also retain metadata required for retrieval and traceability.

---

## 12. Embedding Generation

Each document chunk is converted into a numerical vector representation.

**Embedding Flow:**

```
Document Chunk
    ↓
Embedding Model
    ↓
Vector Representation
    ↓
Vector Database
```

**Key Design Principle:** The same embedding approach is used during query-time retrieval so that the query and stored document chunks can be compared in a common vector space.

---

## 13. Vector Database and Semantic Search

**Workflow:**

| Step | Description |
|---|---|
| 1 | Query is converted into an embedding |
| 2 | Vector database is searched |
| 3 | Similar document vectors are identified |
| 4 | Corresponding document chunks are retrieved |
| 5 | Most relevant chunks become context for LLM |

**Semantic Search Flow:**

```
User Query → Query Embedding → Semantic Search → Ranked Results → Retrieved Chunks
```

---

## 14. Context Retrieval

The retrieved chunks are combined into a context package.

**Context Construction:**

```
User Query
    +
Retrieved Documents
    ↓
Context Builder
    ↓
Relevant Context
```

**Key Design Principle:** The objective is to provide the LLM with information that is directly relevant to the user's query rather than passing the entire document collection.

---

## 15. Prompt Construction

After retrieval, the AI Engine constructs the final prompt.

**Prompt Components:**

```
System Instructions
    +
User Query
    +
Retrieved Context
    +
Response Instructions
    ↓
Final Prompt
```

**Prompt Architecture:**

| Component | Description |
|---|---|
| System Instructions | Define AI behavior and constraints |
| User Query | Original user question |
| Retrieved Context | Relevant document chunks (RAG) |
| Prediction Results | ML model output (ML path) |
| Response Instructions | Format and style guidance |

**Key Design Principle:** For ML queries, the prompt may contain the model prediction or structured result when natural-language explanation is required. For RAG queries, the prompt contains the retrieved document context.

---

## 16. Llama 3.1 and Ollama Inference

The CARIVIX AI Engine uses Llama 3.1 as the selected LLM, with Ollama providing local inference.

**Inference Flow:**

```
Final Prompt
    ↓
Llama 3.1
    ↓
Ollama
    ↓
Generated Response
```

**Key Design Principle:** The local inference approach provides an AI execution layer that can operate without sending the prompt to an external hosted LLM API.

---

## 17. General LLM Query Workflow

Queries that do not require structured ML prediction or document retrieval can be routed to the general LLM path.

**General LLM Flow:**

```
User Query
    ↓
Query Preprocessing
    ↓
Intent Classification
    ↓
Query Router → General LLM Path
    ↓
Prompt Construction
    ↓
Llama 3.1 + Ollama
    ↓
Response Processing
    ↓
API Response
```

**Key Design Principle:** The LLM should not be treated as the replacement for the ML model. Instead, it acts as the language-generation/reasoning component within the hybrid architecture.

## 18. Hybrid AI Query Workflow

The complete CARIVIX architecture integrates all three processing paths:

```
User Query
    ↓
API Request (FastAPI)
    ↓
Query Preprocessing
    ↓
Intent Classification (TF-IDF + Logistic Regression)
    ↓
Query Router
    ↓
    ├── ML Prediction Path ──→ Model Service ──→ Prediction
    ├── RAG Path ────────────→ Semantic Search ──→ Context Retrieval

    ↓
Context/Prediction Construction

```

## 19. End-to-End Sequence

The following represents the complete request lifecycle:

| Step | Action | Description |
|---|---|---|
| 1 | Query Submission | User submits natural-language query through AI API |
| 2 | API Validation | FastAPI validates incoming request |
| 3 | Query Preprocessing | Query is normalized and prepared for classification |
| 4 | Intent Classification | TF-IDF + Logistic Regression predicts intent and confidence |
| 5 | Query Routing | Router selects appropriate AI processing pipeline |
| 6A | ML Processing | Model service validates inputs, loads baseline model, performs inference, generates prediction |
| 6B | RAG Processing | Query embedded, semantically searched, relevant chunks retrieved |
| 6C | General LLM Processing | Query passed toward prompt construction |
| 7 | Context/Result Construction | Selected pipeline provides prediction, context, or query |
| 8 | Prompt Construction | AI Engine constructs final prompt |
| 9 | LLM Inference | Llama 3.1 + Ollama processes final prompt |
| 10 | Response Processing | Generated output validated and formatted |
| 11 | API Response | FastAPI returns final response to client |

## 21. Error Handling Workflow

The AI Engine validates the request at every major processing boundary.

**Failure Scenarios:**

| # | Failure Scenario | Description |
|---|---|---|
| 1 | Invalid Request | Malformed or incomplete request |
| 2 | Missing Query | No query provided |
| 3 | Invalid Model Input | Incorrect feature format |
| 4 | Intent Classification Failure | Unable to classify intent |
| 5 | Low-Confidence Intent | Confidence below threshold |
| 6 | Model Loading Failure | Unable to load ML model |
| 7 | Model Inference Failure | Error during inference |
| 8 | Retrieval Failure | Unable to retrieve documents |
| 9 | Empty Retrieval Result | No relevant chunks found |
| 10 | LLM Inference Failure | Error during LLM generation |
| 11 | Invalid Generated Response | Response format invalid |

**Error Handling Flow:**

```
Request Validation
    ↓
Query Validation
    ↓
Intent Classification
    ↓
Routing
    ↓
Pipeline Execution
    ↓
Response Validation
    ↓
Error Handling (if applicable)
```

---

## 22. Response Processing

Before returning the result to the client, the response passes through a response-processing layer.

**Response Processor Responsibilities:**

| Responsibility | Description |
|---|---|
| Validate Output | Check output structure and format |
| Normalize Response | Standardize response format |
| Preserve Predictions | Keep prediction values intact |
| Format Generated Text | Ensure proper text formatting |
| Return Status | Include appropriate status information |
| Prevent Malformed Output | Block invalid output from reaching client |

**Response Flow:**

```
ML/RAG/LLM Result
    ↓
Response Processor
    ↓
Output Validation
    ↓
Response Formatting
    ↓
FastAPI
    ↓
Client
```

## 23. Model Configuration

Model configuration is kept separate from core inference logic.

**Configuration Elements:**

| Element | Description |
|---|---|
| Model Name | Name of the model |
| Model Version | Version identifier |
| Model Path | File path to model artifact |
| Input Schema | Expected input format |
| Output Schema | Expected output format |
| Inference Parameters | Runtime inference settings |
| Environment Settings | Environment-specific configuration |

**Configuration Flow:**

```
Model Service
    ↓
Model Configuration
    ↓
Model Loader
    ↓
Trained Model
```

**Key Design Principle:** The model service reads the appropriate configuration before loading the model, allowing the model artifact or model version to be changed without redesigning the entire query workflow.
