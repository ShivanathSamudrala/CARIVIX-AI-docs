## 1. Overview

The CARIVIX AI Voice Module provides a voice-based interface through which users can interact with the CARIVIX platform using natural language. The module accepts voice or text input, converts speech into text, identifies the user's intent, extracts required parameters, routes the request to the appropriate CARIVIX module, generates a response, and optionally converts the response back into speech.

The architecture is designed to support multilingual voice interaction and conversational workflows while allowing the underlying NLP and voice technologies to be independently upgraded.

---

## 2. Architecture Overview

The Voice Module follows a sequential processing architecture:

```
Voice Input / Text Input
        ↓
Activation Layer (IDLE → ACTIVATED → LISTENING)
        ↓
Speech-to-Text (Whisper) → Transcribed Text
        ↓
Intent Classification → Intent + Confidence Score
        ↓
Confidence Decision (High/Medium/Low)
        ↓
Parameter/Entity Extraction
        ↓
Intent Router
        ↓
CARIVIX Module Execution
        ↓
Result Generation
        ↓
Response Generator
        ↓
Text-to-Speech (TTS) + Visual Response
        ↓
Conversation Continuation (Continue/End)
```

---

## 3. Input Modes

The Voice Module supports two input modes:

| Input Mode | Description | Example |
|---|---|---|
| Voice Input | User speaks a command through a microphone | "Show the map of Hyderabad." |
| Text Input | User directly enters a text command | "Show the map of Hyderabad." |

Text input can bypass the Speech-to-Text stage and proceed directly to intent classification.

---

## 4. Activation Layer

The assistant starts in an **IDLE** state. The system can be activated through:

| Activation Method | Description |
|---|---|
| Wake Word | Voice-activated trigger |
| Assistant Trigger | Button or command-based activation |
| User Input | Direct interaction |

Once activated, CARIVIX responds with an acknowledgement such as: *"I'm listening."*

The system then transitions to the LISTENING state.

**State Flow:** `IDLE → ACTIVATED → LISTENING`

---

## 5. Listening Layer

The Listening component captures the user's voice input.

| Responsibility | Description |
|---|---|
| Activate Microphone | Start audio capture |
| Record Speech | Capture user's voice input |
| End Detection | Determine when the user has finished speaking |
| Forward Audio | Send captured audio to STT component |

**State:** `IDLE → ACTIVATED → LISTENING`

---

## 6. Speech-to-Text Layer

### 6.1 Selected Technology: Whisper

The current architecture uses **Whisper-Small** as the Speech-to-Text component. The STT layer converts captured audio into text.

```
Audio Input
    ↓
Whisper STT
    ↓
Transcribed Text
```

**Example:**

| Audio | STT Output |
|---|---|
| "Show the map of Hyderabad." | Show the map of Hyderabad |

The transcribed text is then passed to the Intent Classifier.

### 6.2 STT Technologies Evaluated

| Technology | Status |
|---|---|
| Whisper-Small |  Selected for current architecture |
| Vosk |  Evaluated (alternative) |
| Google Speech |  Evaluated (alternative) |
| Azure Speech |  On Hold (paid service) |

### 6.3 Key Design Decision

Azure Speech is kept on hold because it is a paid service. The selected architecture uses Whisper as the current STT engine while keeping the STT layer modular enough to allow alternative engines to be integrated later.

---

## 7. Intent Classification Layer

The Intent Classifier determines what the user is trying to accomplish. The classifier receives the text generated by the STT layer and predicts:

| Output | Description |
|---|---|
| Intent | The identified user intent |
| Confidence Score | Probability score for the prediction |

**Example:**

| Input | Output |
|---|---|
| "Show the map of Hyderabad." | Intent: `gis_query`, Confidence: `0.87` |

The confidence score determines the next processing path.

---

## 8. Confidence Decision

The architecture uses confidence-based decision making:

| Confidence Level | Threshold | Action |
|---|---|---|
| High Confidence | ≥ 0.80 | Directly execute the identified intent |
| Medium Confidence | 0.40 – 0.80 | Request clarification from the user |
| Low Confidence | < 0.40 | Ask user to repeat or rephrase the command |

### 8.1 High Confidence Flow

```
Intent Classification
        ↓
Confidence ≥ 0.80
        ↓
Execute Intent
```

### 8.2 Medium Confidence Flow

**Example:**

```
CARIVIX: "Did you want me to show the Hyderabad map or compare district development?"
User: "Hyderabad map."
```

The clarified request is then processed.

### 8.3 Low Confidence Flow

**Example:**

```
CARIVIX: "I didn't understand that. Could you please repeat?"
```

This prevents incorrect actions caused by uncertain intent predictions.

## 9. Parameter / Entity Extraction

After determining the intent, the system extracts the parameters required to execute the request.

**Example:**

| Command | Intent | Entities |
|---|---|---|
| Show the AQI in Hyderabad. | gis_query / relevant information query | City: Hyderabad, Metric: AQI |

**Possible Parameters:**

| Parameter | Description |
|---|---|
| City | Target city |
| District | Target district |
| Date | Target date |
| Time | Target time |
| Metric | Specific metric (AQI, traffic, etc.) |
| Product | Product name |
| Report Type | Type of report |
| Location | Geographic location |
| Category | Data category |

The extracted entities are passed to the Intent Router.

## 14. Text-to-Speech Layer

The architecture contains a dedicated Text-to-Speech (TTS) layer. Its purpose is to convert the generated textual response into spoken audio.

```
Generated Response
        ↓
TTS
        ↓
Audio Response
```

**Current Status:**

| Component | Status |
|---|---|
| TTS Technology | ⏳ To Be Finalized |

**Design Principle:** The TTS component should remain modular so that the selected technology can be integrated without changing the rest of the Voice Module architecture.

## 15. Response Delivery

The final response is delivered through two channels:

| Channel | Description | Example |
|---|---|---|
| Visual Response | Result displayed on the CARIVIX interface | Map display |
| Voice Response | Result converted to speech and played back | "Here is the Hyderabad map." |

**Example:**

```
CARIVIX:

Voice: "Here is the Hyderabad map."
```

---

## 16. Conversation Continuation

After delivering the response, the system determines whether the conversation should continue.

### 16.1 Continue Flow

If the user wants to continue:

```
Response
        ↓
Continue Conversation
        ↓
LISTENING
```

### 16.2 End Flow

If the user ends the conversation:

```
Response
        ↓
End Session
        ↓
IDLE
```

This allows CARIVIX to support multi-turn conversational interaction.

## 17. Special Conversation Flows

The Voice Module supports several special flows:

| Flow | Description | Example |
|---|---|---|
| Confirmation Flow | Request confirmation for sensitive actions | "Shall I proceed?" |
| Cancel Flow | User cancels an operation | "Cancel", "Stop", "Never mind", "Go back" |
| Repeat Flow | User requests previous response again | "Repeat that." |
| Contextual Follow-up | System uses conversation context for follow-up commands | User: "Hyderabad." (associated with previous request) |
| Error Handling | User-friendly responses for failures | "I couldn't understand the request. Please try again." |

### 17.1 Confirmation Flow

For important or potentially sensitive actions, the assistant can request confirmation. The action is executed only after confirmation.

### 17.2 Cancel Flow

The user can cancel an operation using commands such as:

- Cancel
- Stop
- Never mind
- Go back

The system safely terminates the pending action.

### 17.3 Repeat Flow

The user can request the previous response again.

**Example:**

```
User: "Repeat that."
CARIVIX: [Repeats the previous response]
```

### 17.4 Contextual Follow-up

The system can use conversation context to understand follow-up commands.

**Example:**

```
CARIVIX: "Which city would you like to check?"
User: "Hyderabad."
```

The system associates "Hyderabad" with the previously requested operation.

### 17.5 Error Handling

The system should provide user-friendly responses for:

| Error Scenario | Example Response |
|---|---|
| Speech not recognized | "I couldn't hear you clearly. Please try again." |
| Intent not recognized | "I didn't understand that request." |
| Low confidence | "Could you please rephrase that?" |
| Missing parameters | "I need more information to complete your request." |
| Backend/API failure | "The system is temporarily unavailable. Please try again later." |
| Data unavailable | "The information you requested is not available." |
| Invalid command | "I don't recognize that command. Please try again." |

## 21. Architecture Design Principles

| Principle | Description |
|---|---|
| Modularity | STT, NLP, entity extraction, routing, TTS, and response generation are separate components |
| Replaceability | STT layer can accommodate alternative technologies without redesigning the complete pipeline |
| Multilingual Support | Architecture is designed around multilingual voice commands |
| Confidence-Aware Processing | System does not blindly execute uncertain predictions |
| Conversational Context | Supports clarification and contextual follow-up interactions |
| Fault Tolerance | Error handling and fallback paths are incorporated |
| Scalability | Individual components can be independently optimized, replaced, or scaled |
